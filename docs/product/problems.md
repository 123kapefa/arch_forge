# Проблемы и правила

Анализатор ищет проблемы архитектуры и расхождения с правилами проекта. Каждая находка несёт идентификатор правила, серьёзность (`Info` / `Warning` / `Error`) и источник.

## Каталог правил
| Идентификатор | Категория | Что находит |
|---|---|---|
| `shared-db` | архитектура | общая БД у нескольких сервисов |
| `shared-store` | архитектура | общее хранилище (например, Redis) у нескольких сервисов |
| `service-cycle` | архитектура | циклы между сервисами (учитывается уверенность связи) |
| `dangling-event` | архитектура | событие публикуется, подписчика нет (направление из кода, только при полной картине по шине; см. [Картина системы](system-picture.md)) |
| `orphaned-subscription` | архитектура | есть подписка, издателя нет (то же условие) |
| `exposed-datastore` | архитектура | порт хранилища опубликован наружу |
| `layer-violation` | архитектура | нарушено направление зависимостей слоёв Clean Architecture |
| `drift` | свод | тип не соответствует правилам роли (например, хендлер без маркерного интерфейса) |
| `dto-mapping` | свод | DTO собирается инлайн в нескольких местах вместо маппера |
| `redundant-null-check` | свод | `ArgumentNullException.ThrowIfNull(p)` (а также `if (p == null) throw …` и `p ?? throw …`) на ненулевом параметре: за нули отвечает Nullable, границу API проверяет валидатор |
| `custom:<id>` | свод | ваши [свои правила](profiles.md#свои-правила) |

Строгость каждого правила и параметры (порог уверенности циклов, минимум мест для `dto-mapping`) задаются в [профиле проекта](profiles.md). Выключенное правило остаётся видимым в сводке как выключенное.

## Здоровье
Каждый узел (система, сервис, слой) получает цветовой показатель по числу и серьёзности проблем внутри: он подсказывает, куда проваливаться.

## Покрытие
Тип классифицируется тремя способами: по **маркеру** (точно), по **эвристике** (по имени, например суффикс `Handler`) или остаётся **unknown**. Доли показываются честно; неоднозначное не выдумывается.

## Деградация
Если часть проекта не разобрана (нет `bin/`, файл слишком большой, ошибка разбора), это помечается явно, а остальное всё равно показывается.

## Правило «лишняя проверка на null»
Источник — методичка «Стратегия ошибок и нулей», правило 3: внутри сервиса ненулевой параметр проверяет компилятор, проверка в коде избыточна. Находка уровня сервиса (Info, категория «свод»), включается вместе с линзой «дрейф от свода», на уровне Simple выключена, как и остальные мягкие правила свода.

Находится только там, где параметр метода, конструктора (в том числе первичного) или локальной функции имеет ненулевой тип, а в этом месте включён nullable: директивы `#nullable enable/disable/restore` применяются по позиции, как в компиляторе (`warnings` аннотации не включает), общая настройка берётся из `<Nullable>` в csproj или `Directory.Build.props/.targets` (читается как XML: комментарии и `Condition` игнорируются; видны файлы в папке разбора и на уровень выше). Не считаются лишними: `T?`, `Nullable<T>`, значимые типы (`int`, `Guid`, `DateTime` и т. п.), параметры `ref/out/in`, со значением по умолчанию `null`, с `[AllowNull]`/`[MaybeNull]`, типы-параметры дженериков, проверки не самого параметра (поля, свойства, локальные переменные), параметры лямбд, параметры record (это свойства) и параметры, перекрытые одноимённым полем или свойством. Слои tests, Contracts и Shared не судятся: публичное API библиотеки вызывают и без nullable. Разбор синтаксический: тип берётся из написанного, псевдонимы и неявные типы не раскрываются; формы `throw new(...)` без типа и условия с `||` не распознаются. Код читается только когда включена линза свода и правило не выключено.
