# Проблемы и правила

Анализатор ищет проблемы архитектуры и расхождения с правилами проекта. Каждая находка несёт идентификатор правила, серьёзность (`Info` / `Warning` / `Error`) и источник.

## Каталог правил
| Идентификатор | Категория | Что находит |
|---|---|---|
| `shared-db` | архитектура | общая БД у нескольких сервисов |
| `shared-store` | архитектура | общее хранилище (например, Redis) у нескольких сервисов |
| `service-cycle` | архитектура | циклы между сервисами: в цикл входят только связи с уверенностью не ниже порога профиля (по умолчанию 0.8). Подсвечиваются **все** сервисы цикла (не только один); у находки есть список участников и уверенность — по самой слабой связи цикла |
| `dangling-event` | архитектура | событие публикуется, подписчика нет (направление из кода, только при полной картине по шине; см. [Картина системы](system-picture.md)) |
| `orphaned-subscription` | архитектура | есть подписка, издателя нет (то же условие) |
| `exposed-datastore` | архитектура | порт хранилища опубликован наружу; в среде prod — `Critical`, в dev — не находка |
| `missing-env-key` | архитектура | код читает ключ конфигурации, а в выбранной среде его никто не задаёт (секреты — только именем) |
| `layer-violation` | архитектура | нарушено направление зависимостей слоёв Clean Architecture |
| `di-captive` | архитектура | в DI-контейнере сервиса Singleton держит Scoped (например, `DbContext`), в том числе через цепочку Transient; только с высокой уверенностью |
| `di-lifetime-hint` | архитектура (`Info`) | мягкий вид: Singleton держит Transient, либо Scoped со средней/низкой уверенностью; здоровье не красит |
| `di-missing` | архитектура | зависимость конструктора своего типа нигде не зарегистрирована в DI — упадёт при создании объекта |
| `drift` | свод | тип не соответствует правилам роли (например, хендлер без маркерного интерфейса) |
| `dto-mapping` | свод | DTO собирается инлайн в нескольких местах вместо маппера |
| `redundant-null-check` | свод | `ArgumentNullException.ThrowIfNull(p)` (а также `if (p == null) throw …` и `p ?? throw …`) на ненулевом параметре: за нули отвечает Nullable, границу API проверяет валидатор |
| `mixed-error-strategy` | свод | в одном сервисе ожидаемые ошибки и возвращают (`Result`), и бросают (`NotFoundException`, `ConflictException`, `ValidationException`…): нужна одна стратегия на сервис |
| `double-validation` | свод | формат или длину поля проверяет валидатор (FluentValidation), хотя в сервисе есть Value Object с похожим именем (совпадает с полем или оканчивается на него) и строковой фабрикой: у правила должен быть один владелец |
| `aggregate-time` | свод | агрегат сам читает часы (`DateTime.UtcNow` в слое Domain) или аудит-поля (`CreatedAt`/`UpdatedAt`) ставит interceptor/`SaveChanges`: время должно приходить в метод агрегата параметром |
| `aggregate-events` | свод | публичная мутация агрегата (слой Domain) меняет состояние, но не поднимает доменное событие (`RaiseDomainEvent`/`AddDomainEvent`/`_domainEvents.Add`) или не обновляет `UpdatedAt`, хотя другие методы типа его ставят. Агрегатом считается тип, который сам где-то поднимает события, или наследник `*AggregateRoot`. Не судятся: конструкторы, статические фабрики, закрытые методы, `partial`-типы, `Apply*`/`When*`, тесты. Вызов своего метода, который поднимает событие или ставит время, засчитывается. Эвристика синтаксическая: намеренно «тихую» мутацию игнорируйте или выключите правило |
| `folder-structure` | свод | код разложен по техническому признаку: папки `Common`/`Utils`/`Helpers`/`Services`/`Managers`, `Commands`/`Queries` вне `Features/{Entity}`, файлы `*Manager`/`*Helper`/`*Resolver`/`*Processor`/`*Util`: раскладывайте по сущности |
| `custom:<id>` | свод | ваши [свои правила](profiles.md#свои-правила) |

У каждого вида находок есть подсказка «как чинить» (в том числе у пробелов покрытия `unattributed-calls` и `ambiguous-target`).

Строгость каждого правила и параметры (порог уверенности циклов, минимум мест для `dto-mapping`) задаются в [профиле проекта](profiles.md). Выключенное правило остаётся видимым в сводке как выключенное.

## Проверка DI-контейнера
Правила `di-captive`, `di-lifetime-hint` и `di-missing` читают регистрации сервиса (`AddSingleton/AddScoped/AddTransient`, `TryAdd*`, keyed-варианты, `AddDbContext`, `AddHostedService`, `AddHttpClient<T>`, `AddRefitClient<T>`, `AddGrpcClient<T>`, `ServiceDescriptor.*<…>`) по всему коду сервиса, включая свои методы-расширения, и зависимости из конструкторов (в том числе основных). Тесты в проверку не входят. Запускаются вместе с анализом кода (галочка «нарушения слоёв»); отдельного переключателя нет.

Каждая находка содержит место регистрации (`файл:строка`) и **уверенность** в примечании:
- **высокая** — прямая цепочка «регистрация → конструктор»;
- **средняя** — у типа несколько регистраций с разным временем жизни, у класса несколько конструкторов (без `[ActivatorUtilitiesConstructor]`), либо Singleton держит Transient;
- **низкая** — зависимость выведена из тела фабрики (`sp => …`) либо набор регистраций неполон.

Серьёзность: `Warning` получают только находки с высокой уверенностью (`di-captive`; `di-missing` с хотя бы одной высокой). Всё остальное — `Info` (`di-lifetime-hint`) или отметка покрытия (`di-missing` без высокой уверенности) и на здоровье не влияет. Singleton → Transient вынесен в мягкий `di-lifetime-hint`, потому что Transient в Singleton обычно безобиден.

Набор регистраций считается **неполным**, если встретилось сканирование сборок (Scrutor, MediatR, FluentValidation, MassTransit), неизвестная форма регистрации (экземпляр, `new ServiceDescriptor(…)`, тип из переменной, `AddRefitClient(typeof(…))`) или разбор урезан по числу файлов. Тогда «не зарегистрировано» идёт только с низкой уверенностью. Если регистраций не найдено вообще (другой контейнер, DI собирается в другом проекте), `di-missing` молчит.

«Не зарегистрировано» проверяется только для типов, объявленных в самом сервисе (интерфейсы и конкретные классы), и только для обязательных параметров: типы фреймворка и пакетов, коллекции, `Func`/`Lazy`, nullable и параметры со значением по умолчанию не проверяются. Контроллеры проверяются без регистрации. Регистрации по ключу (`AddKeyed*`) считаются регистрациями типа, но не участвуют в проверке времён жизни. Регистрации из расширений за пределами сервиса (общий пакет) не видны. Перечень в одной находке ограничен 1000 записей, полное число — в названии.

**Оговорка про профиль.** Эти правила пока не внесены в каталог правил профиля: их строгость и выключение в [профиле](profiles.md) не настраиваются, они работают с собственной серьёзностью детектора.

## Здоровье
Каждый узел (система, сервис, слой) получает цветовой показатель по числу и серьёзности проблем внутри: он подсказывает, куда проваливаться.

## Покрытие
Тип классифицируется тремя способами: по **маркеру** (точно), по **эвристике** (по имени, например суффикс `Handler`) или остаётся **unknown**. Доли показываются честно; неоднозначное не выдумывается.

**Покрытие системы** (`coverage` в `/api/system`) — сумма по всем разобранным сервисам: `marker + heuristic + unknown = total` (число типов). У каждого сервиса в `services[].coverage` — его собственная разбивка. Сервис, который не разобрался, в сумму не входит (это пропуск, а не «unknown») и отдельно назван в `degradations`. Так же в `degradations` попадает сервис, в котором больше 20 000 файлов `.cs`: разбирается только первая часть, и карта по нему честно помечена неполной. Пока код не анализировался (линзы выключены), разбивки нет: все три доли нулевые, `total` — число узлов, обзор пишет «нет данных».

## Деградация
Если часть проекта не разобрана (нет `bin/`, файл слишком большой, ошибка разбора), это помечается явно, а остальное всё равно показывается.

## Правило «лишняя проверка на null»
Источник — методичка «Стратегия ошибок и нулей», правило 3: внутри сервиса ненулевой параметр проверяет компилятор, проверка в коде избыточна. Находка уровня сервиса (Info, категория «свод»), включается вместе с линзой «дрейф от свода», на уровне Simple выключена, как и остальные мягкие правила свода.

Находится только там, где параметр метода, конструктора (в том числе первичного) или локальной функции имеет ненулевой тип, а в этом месте включён nullable: директивы `#nullable enable/disable/restore` применяются по позиции, как в компиляторе (`warnings` аннотации не включает), общая настройка берётся из `<Nullable>` в csproj или `Directory.Build.props/.targets` (читается как XML: комментарии и `Condition` игнорируются; видны файлы в папке разбора и на уровень выше). Не считаются лишними: `T?`, `Nullable<T>`, значимые типы (`int`, `Guid`, `DateTime` и т. п.), параметры `ref/out/in`, со значением по умолчанию `null`, с `[AllowNull]`/`[MaybeNull]`, типы-параметры дженериков, проверки не самого параметра (поля, свойства, локальные переменные), параметры лямбд, параметры record (это свойства) и параметры, перекрытые одноимённым полем или свойством. Слои tests, Contracts и Shared не судятся: публичное API библиотеки вызывают и без nullable. Разбор синтаксический: тип берётся из написанного, псевдонимы и неявные типы не раскрываются; формы `throw new(...)` без типа и условия с `||` не распознаются. Код читается только когда включена линза свода и правило не выключено.

## Правило «хранилище опубликовано наружу» по средам
БД/кэш с портом, опубликованным на все интерфейсы (без `host_ip` или `0.0.0.0`/`::`), — находка, серьёзность зависит от выбранной среды (`?env=`, имя берётся из `docker-compose.<среда>.yml`):

| Среда | Серьёзность |
|---|---|
| `prod`, `production`, `prd`, `live` | `Critical` («в среде prod») |
| `dev`, `development`, `local`, `test`, `testing`, `ci` | не находка: открытая БД на машине разработчика ожидаема |
| остальные (`stage`, «по умолчанию» = base + override, незнакомые имена) | `Warning`: «в prod» без подтверждения именем среды не утверждается |

Привязка на `127.0.0.1`/`::1` и порты обычных сервисов не флагаются. Источник — файл и строка записи `ports` (из оверлея среды или из base; путь относительно корня анализа) в раскрытии находки.

## Правило «не хватает ключа конфигурации»
Для выбранной среды сверяются ключи, которые **читает код** сервиса (`config["A:B"]`, `GetSection("A")["B"]`, `GetValue<T>("A:B")`, `GetConnectionString("n")`), с тем, что задано в `environment`/`env_file` его compose-сервиса этой среды и в `appsettings.json` / `appsettings.<Среда>.json` (файлы чужих сред не учитываются; `__` в env равносилен `:`). Находка уровня сервиса (`Warning`) перечисляет недостающие ключи с местом чтения в коде; ключи, похожие на секреты (пароль, токен, ключ API, строка подключения…), помечены «секрет».

**Значения не выводятся и не хранятся нигде:** ни из compose, ни из appsettings, ни из кода — только имена ключей. Включается вместе с линзами, читающими код (дрейф, слои, вызовы).

Что не считается недостающим: ключи с запасным значением (`config["X"] ?? "default"`, `GetValue<T>("X", default)`), платформенные ключи ASP.NET (`Logging:*`, `ASPNETCORE_*`, `DOTNET_*`, `Kestrel:*`, `AllowedHosts`, `urls`), записи `environment: [KEY]` без `=` (проброс из окружения хоста — ключ задан). Если у сервиса есть `env_file`, который не удалось прочитать (нет файла, лежит вне корня анализа, ссылка), находка не выдаётся: ключи из него неизвестны.

Ограничения: значения из внешнего окружения (секреты оркестратора, vault, переменные хоста) статикой не видны; не охвачены свойства `IOptions<T>` и ключи, заданные не строковым литералом; чтение конфигурации распознаётся по получателю `config`/`configuration`/`cfg` и по цепочке `GetSection("A")["B"]`. Сервис без привязанного узла compose получает находку только если его узел определяется однозначно (единственный сервис в compose или единственный с совпадающим именем). Пометка «секрет» стоит в начале пояснения к ключу (отдельного поля в контракте нет); определяется по целым словам имени, значения не анализируются.

## Правило «смесь стратегий ошибок»
Источник — методичка «Стратегия ошибок и нулей», правило 1: на проект одна стратегия, в сервисе одну ожидаемую ошибку нельзя то возвращать, то бросать. Находка уровня сервиса (Info, категория «свод»), включается вместе с линзой «дрейф от свода», на уровне Simple выключена.

Срабатывает, когда в сервисе есть и методы, возвращающие `Result` / `Result<…>` (в том числе внутри `Task<>`/`ValueTask<>`), и броски `throw new …Exception`, где в имени исключения есть `NotFound`, `Conflict`, `Validation`, `Forbidden`, `Unauthorized`, `AlreadyExists`, `BadRequest` или `Duplicate`. В списке показывается меньшинство, то есть отклонение от преобладающей стратегии (при равенстве — броски). Не считаются смесью «мосты», где вернуть значение нельзя: конструкторы, аксессоры свойств, операторы, типы `*Behavior`, `*Middleware`, `*ExceptionHandler`, `*Converter`, `*Filter`, `*Interceptor`; свойства с телом-выражением; слои tests, Contracts и Shared; методы без тела (интерфейсы) и фабрики собственного типа `Result`. Сравниваются методы с методами (несколько бросков в одном методе — один). Броски в слое Domain (инварианты агрегатов и value object) учитываются так же, как в остальных слоях. Ошибки программиста (`ArgumentException`, `InvalidOperationException`, `UnreachableException`) и повторный `throw;` не учитываются. Разбор синтаксический: тип результата и исключения берётся из написанного имени (свой тип `Result` с другим смыслом тоже посчитается). Код читается только когда включена линза свода и правило не выключено.

## Правило «двойная валидация»
Источник — методичка «Валидация — один раз»: у каждого правила один владелец; поле с Value Object проверяет VO (`Of`), валидатор формат и длину не повторяет. Находка уровня сервиса (Info, категория «свод»), включается вместе с линзой «дрейф от свода», на уровне Simple выключена.

Срабатывает, когда валидатор (класс от `AbstractValidator<T>`) проверяет поле цепочкой `MaximumLength`, `MinimumLength`, `Length`, `Matches` или `EmailAddress`, а в сервисе есть Value Object (не static/abstract тип со статической фабрикой `Of`/`Create`/`TryCreate`/`Parse`/`From` от строки, которая возвращает сам тип: `T`, `T?` или `Result<T, …>`), имя которого совпадает с полем или оканчивается на него (`Title` ↔ `TagTitle`), либо поле оканчивается на имя VO (`CustomerInn` ↔ `Inn`; имена короче трёх букв так не сопоставляются). Не считаются: `NotNull`/`NotEmpty` (проверка «поле пришло» на границе API — зона валидатора), числовые проверки, цепочки с делегированием VO (`SetValidator`, `MustBe`, а также `Must`/`Custom` с вызовом фабрики, например `Must(Inn.Of)`; обычные бизнес-проверки вроде `MustAsync(NotExist)` делегированием не считаются), слои tests, Contracts и Shared. Поле — два последних сегмента пути (`Customer.Name`), сопоставление идёт по последнему; если подходящих VO несколько, названы все. Не распознаются: `RuleForEach`, правило, сохранённое в переменную, валидаторы через промежуточный базовый класс или `InlineValidator`, лямбды с вызовами (`x.Title.Trim()`). Связь «поле ↔ VO» строится только по имени, поэтому находка — подсказка: если это разные сущности с похожим именем (слаг GitHub-организации и слаг курса), её можно игнорировать или отключить правило в профиле. Код читается только когда включена линза свода и правило не выключено.

## Правило «время и аудит в агрегате»
Источник — методичка «Агрегаты, VO и доменные события»: даты и аудит живут в агрегате, время приходит в его метод параметром (`DateTime now`; источник — `TimeProvider` в хендлере), на проекте один способ. Находка уровня сервиса (Info, категория «свод»), включается вместе с линзой «дрейф от свода», на уровне Simple выключена (там допустим один хук `SaveChanges`).

Срабатывает на два признака. Первый: в слое Domain (проект `*.Domain`) читаются часы — `DateTime.UtcNow`/`Now`/`Today`, `DateTimeOffset.UtcNow`/`Now`. Второй: аудит-поле `CreatedAt`, `UpdatedAt`, `ModifiedAt`, `DeletedAt`, `CreatedOn`, `UpdatedOn` или `LastModifiedAt` присваивается (в том числе через `Property("UpdatedAt").CurrentValue`) в типе, наследующем `SaveChangesInterceptor` или `DbContext`, либо в методе `SaveChanges`/`SaveChangesAsync`/`SavingChanges`, вне слоя Domain. Часы в хендлерах и инфраструктуре, DTO-маппинг с теми же именами полей, слои tests, Contracts и Shared не учитываются. Разбор синтаксический: `TimeProvider.System.GetUtcNow()` в домене, часы через собственную обёртку, `using static System.DateTime`, аудит через `Property(x => x.UpdatedAt)` и `CurrentValues["UpdatedAt"]`, а также вложенные типы внутри `DbContext` не распознаются; слой Domain определяется по сегменту `.Domain` в пути (проект `Svc.Domain`; папка `Domain` без точки в одно-проектном сервисе не распознаётся, а `Svc.Domain.Abstractions` или `.DomainEvents` попадают в Domain). Известные ложные срабатывания: в Domain флагуется любое чтение часов — спецификации (`IsExpired`), собственная реализация часов (`SystemClock`) и события с `= DateTime.UtcNow` по умолчанию; их можно игнорировать или отключить правило в профиле. Код читается только когда включена линза свода и правило не выключено.

## Правило «раскладка по сущности»
Источник — методичка «Структура папок»: папка называется тем, чем владеет код, а не тем, что он такое. Находка уровня сервиса (Info, категория «свод»), включается вместе с линзой «дрейф от свода», на уровне Simple выключена. Код не разбирается, правило смотрит только на пути и имена файлов, поэтому ничего не нагружает.

Папка считается технической, если называется `Common`, `Utils`, `Util`, `Utilities`, `Misc`, `Helpers`, `Helper`, `Managers`, `Services`, `Resolvers` или `Processors` и их единственное число (в любом месте пути; `Services` в слое Infrastructure не считается: там лежат адаптеры внешних систем), либо `Commands`/`Queries` вне `Features/{Entity}` (внутри `Features/Clients/Queries` это правильная раскладка, а `Features/Queries` без сущности нет). Файл считается техническим, если имя оканчивается на `Manager`, `Helper`, `Resolver`, `Processor`, `Util`, `Utils`, `Utility` или их множественное число (`Postprocessor` с маленькой буквы не считается); принятая в методичке абстракция `TransactionManager` (и `ITransactionManager`) и стандартные типы ASP.NET Identity (`UserManager`, `RoleManager`, `SignInManager`, `DependencyResolver`) исключены; частичные файлы вида `Foo.Helper.cs` тоже считаются. Слой tests определяется по подстроке `Test` в пути (как и у остальных правил), поэтому папки вроде `Contest` или `Latest` из проверки выпадают. Слои tests, Contracts и Shared не учитываются. Правило судит по именам, поэтому папка `Services` в рабочем сервисе с обычной доменной логикой тоже попадёт в список: это подсказка пересмотреть раскладку, а не ошибка; ненужное правило можно отключить в профиле.
