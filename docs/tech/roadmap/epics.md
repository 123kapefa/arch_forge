### E2.1 L0 — Система (мульти-сервис) `◧ [B/A]`
- **Что.** Собрать из per-сервисного анализа **единый граф уровня «система»**: узлы = микросервисы + `datastore/topic/external`; рёбра = кросс-сервисные связи (`http-call`, `rw-db`, `uses-bus`), сгруппированные по сервису-владельцу (MsKey).
- **Зачем.** Это **фундамент** всех системных видов (Структура/Deploy/Поток/детекторы). Если группировка «файл → сервис» неверна, весь L0 разваливается — уже ловили на коллизиях ключей (#78/#81/#82).
- **Как.** `MicroserviceLayerBuilder` уже группирует по `/Services/<Name>/` + name-matching (#75) + primary-эвристике (#81). Достроить: (1) узлы `datastore/topic` из compose (E9.1); (2) склейку рёбер «сервис A → сервис B» из http-клиентов (E3.1) и `rw-db` из `DbContext`/репозиториев; (3) дедуп рёбер по `(source,target,kind)`.
- **Готово когда.** На product-site (15 сервисов) L0 показывает все сервисы + их БД/шину + кросс-сервисные рёбра без коллизий; каждый узел открывается в L1.

## E3 — Виды системного уровня

**E3.2 Deploy + среды.** ▣ `[F]` порты/сети/hc/старт по среде на плашках и в инспекторе; переключение dev/stage/prod. Данные — E9.
**E3.3 Сравнение сред.** ▣ `[F]` таблица дифа dev/stage/prod · ◻︎ режим «разделить холст по средам». Данные — E9.

### E3.1 Деривация вызовов на рёбрах (http call-graph) `◧ [A]`
- **Статус.** Срез 0 (вынос `HttpTargetResolver`) + срез 1 (абсолютные URL-литералы: `HttpClient.*Async`, inline `SendAsync`; ребро `http-call` дополняется `EdgeDto.Calls` с `файл:строка`/уверенностью/`matched`; провенанс code; флаг `?calls=`) — сделаны (PR #114). Осталось: срез 2 (относительные URL + base-address), срез 3 (именованный/typed `HttpClient`), срез 4 (Refit); UI-рендеринг списка вызовов в инспекторе. Требует пер-сервисного compose (см. G2-для-анализатора).
- **Что.** Для ребра «сервис A → сервис B» вычислить **список конкретных вызовов** (HTTP-метод + маршрут), которые A делает к B.
- **Зачем.** Клик по ребру должен показывать «что реально идёт» (R17), а не общие слова. Это же — **вход** для потоков (E3.4) и детектора разрыва контракта (E7.4).
- **Как.** Roslyn: найти обращения к (1) типизированным `HttpClient`/генерируемым клиентам (Refit/OpenAPI), (2) `HttpClient.GetAsync/PostAsync("...")`. Сопоставить URL+метод с route-таблицей сервиса B (его endpoints, E4.1). **Уверенность:** типизированный клиент → высокая; строковый литерал URL → средняя; собранный из переменных URL → низкая.
- **Готово когда.** На ребре `gateway → orders` список маршрутов совпадает с реальными вызовами; каждый вызов — с источником (`файл:строка`) и уверенностью.
- **Риск/честность.** Динамические URL не выдумываем — помечаем низкой уверенностью или «не удалось определить маршрут».

### E3.4 Реконструкция потока (sequence по call-graph) `◻︎ [A]`
- **Что.** От входного endpoint развернуть **цепочку вызовов через сервисы**: endpoint → его обработчик → исходящие `http-call`/`publish` → в целевом сервисе снова, и т.д. — собрать последовательность шагов.
- **Зачем.** Показать «что происходит при запросе X» через всю систему; увидеть хрупкие места (длинные синхронные цепочки, внешний вызов на критическом пути) — это E7.3.
- **Как.** Построить call-graph внутри сервиса от action-метода до исходящих вызовов (использует E3.1) и публикаций событий; на границе сервиса продолжить в целевом. Помечать шаг **синхронный** (`await` http) / **асинхронный** (publish в шину).
- **Готово когда.** Для «оформить заказ» строится цепочка `gateway→cart→orders→(postgres, шина)` со стрелками, форматом данных на шаге (E4.1) и пометкой «без рантайма».
- **Ограничение (честно).** Статикой — вероятный happy-path; ветвления/условия/ретраи — рантайм. Всегда помечать «реконструировано по коду, без рантайма».

## E4 — Виды уровня сервиса

**E4.1 Endpoints.** ✔ `[F]` список (verb+route) · ◧ `[A]` **типы запроса/ответа** на endpoint — довести (нужно для конвертаций E3.4 и разрыва контракта E7.4): из сигнатуры action-метода (`[FromBody] T`, возвращаемый `ActionResult<T>`) достать тип DTO входа/выхода.
**E4.3 Оценки.** ◻︎ `[F/A]` грейд сервиса/слоя = агрегат находок (E7) по весам; сам по себе — сводка, не источник истины.

### E4.2 Детект DI (времена жизни, captive, незарегистрированные) `◻︎ [A]`
- **Что.** Прочитать регистрации DI-контейнера сервиса и найти проблемы **времён жизни**.
- **Зачем.** Реальные баги, которые IDE не подсвечивает: **captive dependency** (Singleton держит Scoped → DbContext фактически становится синглтоном: утечки соединений, гонки, «использование после dispose»); **незарегистрированная зависимость** (упадёт в рантайме при резолве); конфликт времён жизни.
- **Как.** Roslyn: распарсить `services.AddSingleton/AddScoped/AddTransient<IX,X>()` и распространённые extension-методы регистрации; для каждого класса собрать зависимости из **конструктора**; построить граф «регистрация → её зависимости» и сверить времена жизни: Singleton, зависящий от Scoped/Transient = **captive**; зависимость без регистрации = **missing**.
- **Готово когда.** Для orders-api находится `PaymentService(Singleton) → AppDbContext(Scoped)` как captive (с источником `Program.cs:строка`); для auth-api — незарегистрированный `IPasswordHasher`.
- **Риск.** Регистрации через фабрики/сканирование сборок (Scrutor, `AddSingleton(sp => …)`) — покрыть частые паттерны; экзотику помечать низкой уверенностью, не давать ложных срабатываний.

## E7 — Каталог кросс-сервисных детекторов (payoff арх-ревью) — P3
Ядро ценности «найти проблемы». Каждый детектор = отдельная задача с чётким входом/выходом. Все опираются на граф L0 (E2.1) и провенанс (E5).

### E7.1 Циклы между сервисами `◻︎ [A]`
- **Что.** Найти циклы в графе кросс-сервисных http-зависимостей (`A→B→…→A`).
- **Зачем.** Цикл сервисов = связанность развёртывания, каскадные падения, невозможность независимого релиза — классический арх-смелл; ручным взглядом на 15 сервисов не виден.
- **Как.** На графе L0 с рёбрами `http-call` — поиск сильно связных компонент (Tarjan/Kosaraju). Для каждого цикла — участники + рёбра-виновники с источниками (E5.1).
- **Готово когда.** Если `A→B` и `B→A`, тул показывает цикл с обоими вызовами и их location.

### E7.2 Общая БД (нарушение границ) `◻︎ [A]`
- **Что.** Найти хранилища, в которые пишут **≥2 сервисов**.
- **Зачем.** Общая БД ломает границы сервисов: скрытая связанность, конфликты миграций, нельзя менять схему независимо — частый смертный грех «микросервисов».
- **Как.** По рёбрам `rw-db` (E2.1) сгруппировать по datastore, где >1 писателя; показать «кто пишет» и какие операции/таблицы (E3.1 для db).
- **Готово когда.** postgres с писателями auth+orders помечается как общий, со списком писателей и источниками.

### E7.3 Длинный синхронный путь `◻︎ [A]`
- **Что.** В потоках (E3.4) найти самую длинную цепочку **синхронных** вызовов на пути запроса.
- **Зачем.** Складывающиеся задержки + хрупкость (любое звено роняет весь запрос) — кандидат на асинхронность/кэш/таймаут.
- **Как.** На реконструированном потоке считать длину подряд идущих sync `http-call` до ответа клиенту; учесть внешние вызовы (Stripe) как особо рисковые.
- **Готово когда.** Для «оформить заказ» подсвечивается цепочка из N синхронных сервисов с оценкой риска.

### E7.4 Разрыв контракта `◻︎ [A]`
- **Что.** По цепочке конвертаций/вызовов найти **потерю или несовпадение полей**: продюсер шлёт поле, потребитель его не читает / ждёт отсутствующее; несовпадение версий `/v1`↔`/v2`.
- **Зачем.** Одни из самых дорогих багов интеграции («поле потерялось при маппинге», «версии разъехались») — и они **ловятся статикой** по типам, до рантайма.
- **Как.** Сопоставить тип ответа сервиса B (E4.1) с тем, что сервис A читает после конвертации (E3.1); diff по полям; версии — из route-префикса. Показать оба location.
- **Готово когда.** Если orders маппит ответ и теряет поле, нужное дальше, — тул это показывает с обоими источниками.
- **Риск.** Маппинг через рефлексию/AutoMapper-профили — покрыть явные мапперы; неявное помечать низкой уверенностью.

### E7.5 Конформанс к своду (инварианты-правила) `◻︎ [A]` (доработка lint)
- **Что.** Правила-инварианты команды: «слой X не зависит от Y», «сервис A не пишет в БД B напрямую», «наружу только через gateway» + отчёт нарушений.
- **Зачем.** Перевести мягкий «дрейф» в **жёсткие проверяемые правила** — основа арх-ревью и CI-линтов (Фаза 3). Сейчас есть только нарушения направления слоёв (P1-F) и дрейф.
- **Как.** Расширить convention-pack (`adr/0007`) правилами направления/доступа (декларативно); матчить против графа связей (E2.1); нарушение = находка с источником.
- **Готово когда.** Правило «X→БД Y запрещено» ловит нарушителя и показывает ребро+источник; правило конфигурируется в паке.

## E9 — Парсинг DevOps (данные для системных видов) — [B/A]
Без этого эпика виды Deploy/Сравнение сред стоят на заглушках. Всё — расширение источника, отдающего системную модель.

### E9.1 compose + оверрайды по средам `✔↻ [A]` (расширить `ComposeSystemSource`)
- **Что.** Разобрать `docker-compose.yml` + `docker-compose.<env>.yml`/override → **per-env модель**: сервисы, образы, **порты** (published vs internal), **сети**, **healthcheck**, `depends_on`, ключи `environment`.
- **Зачем.** Это данные для всего DevOps-слоя (Deploy, Сравнение сред, детекторы портов). Сейчас парсер читает сервисы/образы/env/depends — не хватает портов/сетей/hc и merge по средам.
- **Как.** Merge override-файлов по правилам compose для выбранной среды; распарсить `ports`, `networks`, `healthcheck`. Отдать в IR как атрибуты узла-сервиса, зависящие от среды.
- **Сделано (слой 1).** Парсинг `ports`/`networks`/`healthcheck` → `DeployInfo` (E9.1 слой 1).
- **Сделано (слой 2, ч.1).** Движок merge (`ComposeMerge` на «сыром» словаре) + автоприменение `docker-compose.override.yml` — как сам docker compose; влияет и на deploy, и на рёбра (env).
- **Сделано (слой 2, ч.2).** Выбор именованной среды `?env=<name>` (интерфейс/эндпоинт/Map/клиент): merge `docker-compose.<env>.yml` (без override.yml, как `-f base -f <env>`); список сред + активная в контракте (`GraphDto.Environments`).
- **Осталось (UI).** Переключатель сред и вид «Сравнение сред» на фронте (данные готовы: `environments` + per-env deploy).
- **Готово когда.** Для product-site по dev/stage/prod отдаются **разные** порты/сети/hc, видимые в Deploy и в дифе сред. ✔ бэкенд (проверено end-to-end); UI-переключатель — отдельным слайсом.

### E9.2 Публичность портов / границы сетей `◧ [A]`  (часть 1/2 — сделан детектор без среды)
- **Что.** Определить, какие порты **опубликованы на хост** (доступны наружу) в каждой среде, и в какой сети сервис.
- **Зачем.** Killer-находки: «БД наружу в prod», «debug-порт открыт в prod» — то, что реально утекает и опасно.
- **Как.** Из E9.1: `ports: "5432:5432"` = публичный (host:container); `expose`/без host = внутренний. Сопоставить со средой → находка (E7-подобная) с источником `compose.<env>.yml:строка`.
- **Сделано (1/2).** `ExposedPortDetector`: хранилище (Datastore) с портом на все интерфейсы (0.0.0.0 / без host_ip) → `Warning exposed-datastore`; localhost-bind и сервисы не флагаются.
- **Осталось (2/2).** Эскалация по среде (prod → `Critical`) и источник `compose.<env>.yml:строка` — ждёт E9.1 «слой 2» (оверрайды сред).
- **Готово когда.** postgres с публичным портом в prod = critical-находка с источником; в dev — не находка (ожидаемо).

### E9.3 Конфиг/секреты per env `◻︎ [A]`
- **Что.** Какие env-ключи **нужны** сервису и каких **не хватает** в конкретной среде. **Значения не показываем** — только наличие ключей (секреты — только имена).
- **Зачем.** «В prod не хватает переменной X», публичные endpoint'ы без auth — частые провалы развёртывания; безопасность (значения секретов не тащим).
- **Как.** Требуемые ключи — из кода (`Configuration["X"]`, `IOptions<T>`) и compose `environment`; сверить со средой; отметить недостающие; секрет = только имя ключа.
- **Готово когда.** Список «чего не хватает в prod» + пометка «секрет» без значения; не логируем/не выводим значения.
- **Гард.** Соответствует правилу `.claude/rules/secrets-config.md` — значения секретов в отчёты/логи не попадают.

### E9.4 k8s/helm как источник `◻︎ [A]`
- **Что.** Альтернативный источник топологии/деплоя из k8s-манифестов/helm.
- **Зачем.** Не у всех compose; тот же контракт «манифест → системная модель».
- **Как.** Отдельный source с тем же выходным IR, что compose (E9.1).
- **Готово когда.** helm-проект даёт ту же Deploy-модель, что compose-проект.
