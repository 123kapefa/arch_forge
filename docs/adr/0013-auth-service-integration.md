# 0013 — Вход через внешний auth-сервис (Keycloak) с локальным кешем

## Статус
Принято (2026-11-12). Подписки — отдельно и позже.

## Контекст
arch_forge — локальное приложение (`adr/0002`): целевой код не покидает машину. Для пользователей, учётных записей и в будущем подписок есть отдельный сервис авторизации на Keycloak (`auth_service`: проект = realm, приложение = client, права объявляются в коде, пакеты `Platform.Authentication*`, руководство — `docs/embedding-guide.md` в его репозитории). Приложение должно уметь работать без постоянной сети и не требовать от пользователя ставить что-то дополнительно.

## Решение
1. **Вход по сети один раз.** При первом запуске пользователь входит через auth-сервис (OIDC, браузер). Приложение получает токены.
2. **Дальше — локально.** Токены хранятся на машине, не в файле проекта и не в Git. Повторные запуски не требуют сети, пока кеш действителен.
3. **Хранилище токенов — только то, что уже есть в системе, без загрузок.** Windows — DPAPI (встроен в .NET); macOS — Keychain; если системного хранилища нет (Linux без libsecret, контейнер) — зашифрованный файл в каталоге данных пользователя с ключом, привязанным к машине и пользователю, права файла только владельцу. Способ хранения выбирается автоматически и виден в настройках.
4. **Один владелец сессии — Map.** Он делает вход, хранит и обновляет токены; фронт получает только сведения «кто вошёл, до какого срока». Токены во фронт не попадают (в браузерное хранилище не кладём).
5. **Обновление в фоне.** Когда сеть есть, refresh-токен продлевает сессию. Сети нет — работаем по кешу.
6. **Автономная работа — 14 дней** (настройка, значение по умолчанию). За 3 дня до конца в интерфейсе ненавязчивая строка «нужно подключиться к сети». После срока — новый онлайн-вход. Отзыв доступа на сервере вступает в силу при ближайшем подключении. Защита от откручивания часов: запоминаем последнюю виденную дату, время назад — считаем сессию подозрительной и просим вход.
7. **Граница данных.** В auth-сервис уходят только данные входа. Целевой код, карты и профили (`adr/0012`) наружу не передаются.
8. **Где проверяется вход.** Gateway `Map` проверяет токен и применяет права. `Analysis` остаётся без состояния и внутренним: принимает вызовы только от Map (общий внутренний секрет/ключ сервиса и привязка к loopback), прямой доступ снаружи закрыт.
9. **Вход не блокирует функции сейчас.** Без входа всё работает; вход нужен для учётной записи и будущих прав. Блокировка частей приложения — вместе с подписками, отдельным решением.
10. **Режим разработки — всегда есть, но под контролем.** Включается только явным флагом конфигурации *и* только в окружении Development *и* только на loopback; без этого флага сервис не запустится без настроенного входа. Режим выдаёт локальную личность `dev` с ограниченным набором прав (не администратор), в интерфейсе постоянно видна пометка «режим разработки», каждое включение пишется в журнал запуска. Релизная сборка с этим флагом не стартует.

## Как проверять
- **Быстрые тесты:** фиктивный издатель токенов (подписанные тестовые JWT с известным ключом) — проверка токена, срока, прав, часов, льготного периода. Без Keycloak и сети.
- **Интеграционный набор:** Docker-стенд `auth_service` с настоящим Keycloak, запускается вручную/в отдельной задаче CI.

## Не входит
Подписки и тарифы (проектируются позже поверх тех же прав); регистрация собственных пользователей внутри arch_forge; публичная сборка без входа вообще (если понадобится — отдельное решение, режим разработки её не заменяет).

## Альтернативы
- **Вход при каждом запуске.** Ломает работу без сети.
- **Только локальный пароль.** Нет единых пользователей и отзыва доступа.
- **Бессрочный кеш.** Отозванный пользователь остаётся с доступом навсегда.
- **Токены во фронте (localStorage).** Доступны любому скрипту страницы; хранит только Map.
- **Отдельная программа для хранения токенов.** Заставляет пользователя ставить лишнее.

## Последствия
- Нужна безопасная работа с токенами на стороне Map и проверка часов.
- Нужен закрытый внутренний канал Map → Analysis (сейчас Analysis на :5100 без защиты — отдельная задача).
- Режим разработки — единственный путь работы без Keycloak; его защита (флаг + окружение + loopback) должна быть покрыта тестами.

## Срезы реализации
1. Проверка токена в Map, права, режим разработки, закрытие Analysis.
2. Вход (OIDC в браузере), хранилище токенов, фоновое обновление, льготный период и защита часов.
3. Интерфейс: кто вошёл, срок, предупреждение, вход/выход, пометка режима разработки.

## Открытые вопросы
- Способ запуска у пользователей (десктоп-оболочка, браузер, набор сервисов): влияет на то, как открывается окно входа и на какой адрес возвращается OIDC. Пока исходим из того, что Map — единственный процесс с доступом в сеть.
- Какие права объявляет arch_forge в `auth_service` (набор ролей), когда появятся платные функции.

## Статус реализации
- **Срез 1 (#131):** `ArchForge.SharedKernel/Auth` — `AddArchForgeAuth` (три исхода: проверка токена `Authentication:Authority` + `Audience`; режим разработки `Authentication:DevMode=true`; иначе приложение не стартует), `UseInternalGuard` (Analysis принимает вызовы только с loopback и, если задан `Internal:Key`, с этим ключом в заголовке `X-ArchForge-Internal-Key`; без ключа допустимо только в Development). Проверка токена: подпись RS256 по ключам из discovery, `iss`, `aud`, срок (без допуска по времени), токен только из заголовка `Authorization`; имена claims — как в `auth_service` (`sub`, `role`, `permissions`). Пакеты `Platform.Authentication*` не подключены (они из внутреннего фида), используется публичный `Microsoft.AspNetCore.Authentication.JwtBearer`; мгновенный отзыв через Redis — позже. `GET /api/me` (Map) отдаёт сведения о вошедшем. Права проверяет `RequirePermissions(...)`. Существующие эндпоинты пока открыты (решение п. 9); `appsettings.Development.json` Map включает `DevMode`.
- Режим разработки: личность `dev` с правом `archforge.use` (без администраторских), только для запросов с loopback, только Development, не вместе с `Authority`.
- Настройка вне разработки: `Authentication__Authority`, `Authentication__Audience`, `Internal__Key` (одинаковый у Map и Analysis).
- **Вход и закрытие API.** По умолчанию (локальное приложение) существующие эндпоинты открыты, вход их не блокирует (п. 9). Если Map доступен не только с этой машины, включайте `Authentication:RequireLogin=true` (политика по умолчанию — «нужен вошедший») **и** `Auth:AllowLocalSession=false` (запросы принимаются только с токеном). Запросы с loopback считаются локальными: прокси на той же машине (`vite --host`, ssh-туннель) делает чужой запрос «локальным», и при включённой локальной сессии он идёт как вошедший пользователь. Поэтому Map не выставляют в сеть через такие прокси с `AllowLocalSession=true`. Режим разработки (`DevMode`) предназначен только для машины разработчика.
- `Authority` и `InternalAuthority` — только https (http допустим лишь с `AllowInsecureMetadata` в Development); подробности отказа в ответе клиенту скрыты вне Development; допуск по времени токена — 30 с; `Internal:Key` — 16–256 печатных ASCII-символов, обязателен вне Development у обоих сервисов.
- Как запускать локально: окружение `Development` (профиль запуска по умолчанию), `DevMode` берётся из `appsettings.Development.json`.
- **Срез 2 (#132):** вход через браузер (код авторизации + PKCE, публичный клиент `Auth:ClientId`, по умолчанию `archforge-desktop`). В Keycloak у клиента — redirect URI `{Auth:RedirectBaseUrl}/api/auth/callback` (по умолчанию `http://localhost:5200/api/auth/callback`). `POST /api/auth/login` отдаёт адрес входа, браузер возвращается на `GET /api/auth/callback` (состояние одноразовое, живёт 10 минут, не больше 20 незавершённых), затем на `Auth:FrontendUrl` с `?login=ok|failed`. `GET /api/auth/session` — кто вошёл, до какого срока (`none | active | offline | expired | clock | dev`), без токенов; `POST /api/auth/logout`. Все эндпоинты `/api/auth/*` — только с этой машины. Токены держит Map: на диске файл `session.bin` (AES-256-GCM), ключ защищён системой: DPAPI (Windows), Keychain (macOS, утилита `security`), иначе файл `session.key` с правами 0600 (слабее; способ виден в `storage`). Фоновая служба раз в 2 минуты продлевает токены, пока они близки к истечению или связь потеряна; отказ сервера (400/401/403) стирает сессию (доступ отозван), сеть недоступна — работаем по кешу. Автономный срок — `Auth:GraceDays` (14) от последнего успешного обмена; предупреждение за `Auth:WarnDays` (3). Защита часов: хранится самое позднее виденное время, откат больше `ClockToleranceMinutes` (5) даёт состояние `clock` и требует нового входа. Запросы с этой машины без заголовка `Authorization` идут как вошедший пользователь по локальной сессии, пока она пригодна (схема `ArchForgeLocalSession`); с заголовком — как токен.
- **Защита локальной сессии (после ревью среза 2).** Запрос с этой машины без заголовка `Authorization` получает сессию, только если у него нет `Sec-Fetch-Site` (не браузер) или он `same-origin`/`none`; чужой сайт и страница на другом порту этой машины сессии не получают. `POST /api/auth/login|logout` — только same-origin. Вход привязан к браузеру: `/login` ставит HttpOnly-cookie `archforge_login` (Path=/api/auth/callback, Lax), `/callback` сверяет её, поэтому чужой вызов `/login` не подменит аккаунт. Сетевые вызовы к серверу входа идут вне замка сессии (запросы не ждут сеть); отказом считается только `400 invalid_grant` (прочие 4xx — сессию не стирают); свежий refresh-токен держится в памяти, даже если запись на диск упала. По истечении срока токены стираются с диска, остаётся запись «нужен вход».
- **Известные ограничения.** (1) Защита от отката часов работает, пока приложение запущено: если Map не работал, а часы потом выставили назад, метка «последнее виденное время» остаётся прежней. (2) Копию старого `session.bin` можно вернуть: счётчика вне файла нет (DPAPI/Keychain его не хранят). (3) Keychain защищает от чтения файла сессии без доступа к связке (бэкап, другая учётная запись), но не от процессов того же пользователя (запись создана утилитой `security`). Запасной файл ключа (0600, каталог 0700) слабее. Это принятые риски локального приложения.
