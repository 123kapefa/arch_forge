# 0012 — Профили проекта: уровни масштаба и настройка правил

## Статус
Принято в части уровня по умолчанию и пользовательских конфигураций (2026-11-08); остальное — предложено.

## Контекст
Анализатор применяет один и тот же свод ко всем проектам. Встроенный `ConventionPack.Default()` ждёт маркеры большой платформы (`ICommand`, `IEndpoint`, `AbstractValidator`…) и считает отсутствие маркера дрейфом. Для небольшого сервиса это шум: правило верное для платформы, но лишнее для проекта на две сущности (так вышло с Teledok — тестовым заданием, написанным по методичке, которое ревьюер назвал «неоправданно усложнённым»).

Настройки живут в двух местах, и обе плохи для пользователя:
- **JSON-файл в чужом репозитории** (`archforge.conventions.json`, секции `markers`, `fallback`, `expect`, `dtoMapping`; `ConventionPack.Load`). Править его руками неудобно, а положить файл в разбираемый проект не всегда можно.
- **Константы в коде**: порог уверенности циклов `0.8` (`ServiceCycleDetector`), лимиты разбора (`MaxFilesPerScan` 20 000, `MaxReferences` 4 000), списки суффиксов имён сервисов (`-api`, `-service`, … продублированы в `SharedDbDetector`, `ConfigHttpScanner`, `MicroserviceLayerBuilder`), маркеры «сателлитов» (`migrat`, `seed`, `cron`). Поменять их можно только пересборкой.

Методичка (Obsidian, «Platform Architecture») теперь разделена на три уровня проекта — 🟢 простой, 🟡 средний, 🔴 высокий — и содержит таблицу «правило → уровень» (заметки `Уровни проекта` и `Правило → уровень`). Эта таблица и есть источник правил для анализатора.

## Решение
1. **Профиль = уровень + переопределения.** Три уровня: `Simple` (🟢), `Standard` (🟡), `Platform` (🔴). Уровень задаёт значения по умолчанию для каждого правила и порога.
2. **Правило — это данные, а не код.** Каталог правил: идентификатор, категория, строгость по уровням (`Off` / `Info` / `Warning` / `Error`), ссылка на заметку методички. Детекторы читают строгость и пороги из профиля, а не из констант.
3. **Уровень выбирается в приложении.** Анализ идёт по выбранному уровню; по умолчанию — `Standard` (🟡), пока пользователь не выбрал другой. Смена уровня пересчитывает находки без нового разбора кода.
4. **Свои конфигурации анализа.** Пользователь создаёт именованные конфигурации («Для клиента X», «Строгая для платформы»): базовый уровень + свои переопределения правил, порогов и стратегии ошибок. Конфигурацию можно дублировать, переименовывать, привязывать к проекту и экспортировать в `archforge.conventions.json` для команды.
5. **Слои настроек, от слабого к сильному:** уровень по умолчанию → настройки пользователя в приложении → файл `archforge.conventions.json` в проекте (командное соглашение, лежит в репозитории, поэтому сильнее личных настроек).
6. **Настройка через интерфейс.** В приложении выбирается уровень и включается/выключается каждое правило с его строгостью. Профиль сохраняется приложением (по пути проекта), не в разбираемом репозитории. JSON остаётся для продвинутых случаев и общего командного свода.
7. **Уровень подсказывается, а не навязывается.** Сигналы из методички (число сервисов, брокер, маркерные интерфейсы, `Result`) дают совет «похоже на 🟡». Выбор всегда за пользователем; молча менять уровень нельзя (честность, `adr/0008`).
8. **Выключенное правило видно.** Находка и сводка несут идентификатор правила и уровень. Если правило выключено для выбранного уровня, UI говорит «не проверяется на вашем уровне», а не молчит.
9. **Стратегия ошибок — параметр профиля** (`result` / `exceptions` / `auto`). Анализатор определяет её по коду и проверяет именно её; смесь двух стратегий — находка.

### Где что живёт
- Модель профиля и каталог правил — в `Analysis.Core` (анализатор остаётся без состояния: «путь + профиль → результат»).
- Хранение конфигураций и привязок «проект → конфигурация» — в `Map` (он и так владеет пользовательским слоем), профиль передаётся в `Analysis` вместе с запросом. Контракт `ArchForge.Contracts` получает DTO профиля.
- Фронт — окно «Свод конвенций» превращается в окно «Профиль проекта».

### Конфигурация: формат и удобство (обсуждено 2026-11-08)
- **Манифест, а не полная копия.** Конфигурация хранит базовый уровень, версию каталога правил и список отличий; при выходе новых правил она не устаревает. Для публикации из манифеста собирается самодостаточный пакет; опубликованную конфигурацию можно взять за основу (форк).
- **Идентичность и версии.** У конфигурации есть автор, имя и версия; отдельно записаны версия каталога и версия формата манифеста. Так отличаются даже конфигурации одного автора.
- **Содержимое открыто.** Пока не фиксируем, что конфигурация — только данные: формат версионируется, чтобы расширить его позже (тогда понадобится модель доверия).
- **Редактор вместо просмотрщика** (сейчас окно «Свод конвенций» только читает, правка — через JSON-файл в чужом репозитории). Нужны: переключатель строгости у правила, подпись источника значения (уровень / конфигурация / файл проекта), счётчик и фильтр «изменено», поиск и группы по категориям, создание «на основе уровня» или копии.
- **Гибкий сброс:** правило, категория, вся конфигурация; к уровню или к конфигурации-родителю.
- **Предпросмотр влияния:** у каждого правила в каталоге пример «плохо / хорошо», параметр можно двигать и видеть эффект на примере; отдельно — эффект на загруженном проекте.
- **Импорт подключаемый:** файл, вставка JSON, код из каталога конфигураций (по номеру), позже другие источники. Каталог и публикации — отдельное решение после ADR 0013.
- **Три слоя настройки (утверждён функционал макета, 2026-11-08):**
  1. **Правила** — строгость каждого правила (`Off` / `Info` / `Warning` / `Error`), параметры с примером «плохо / хорошо».
  2. **Словарь** — как называются вещи в коде проекта: для каждой роли (команда, запрос, хендлер, валидатор, эндпоинт, агрегат, событие, порт) список маркеров, запасных маркеров и суффиксов. Правила ссылаются на **роли**, а не на имена: поменяли имя в словаре — правила подхватили его сами. Рядом с маркером показывается, сколько типов с ним найдено в проекте (нулевой — подсвечен, вероятно опечатка).
  3. **Свои правила** — конструктор из шаблонов без кода: суффикс → базовый тип; слой не ссылается на слой; запретить тип в папке; роль живёт в папке. У правила название, строгость и автосгенерированный пример. Это данные, их можно публиковать вместе с конфигурацией.
- **Доработать в интерфейсе:** вкладка «Свои правила» самая непонятная (элементы разбросаны); визуальная часть макета — отдельным проходом. Функционал утверждён.
- **Порядок работы:** сначала кликабельный макет окна и решение по удобству, затем срез UI.

### Лимиты разбора — не в профиле (уточнение, срез 1)
`MaxFilesPerScan` (20 000) и `MaxReferences` (4 000) защищают сервер от тяжёлого разбора. Если их берёт профиль, присланный клиентом, любой пользователь сможет поднять лимит и перегрузить Analysis. Поэтому лимиты остаются серверной настройкой (см. E10 «серверные лимиты»); профиль в будущем сможет их только **уменьшать**.

### Имена сервисов (срез 1)
Списки суффиксов (`-api`, `-service`…), суффиксы миграторов и маркеры сателлитов (`migrat`, `seed`, `cron`) собраны в одном месте (`ServiceNaming`) и настраиваются профилем. Исключение: суффиксы ключа слоёв микросервиса и сканер конфигов используют значения по умолчанию, потому что ключ должен совпадать между сборкой слоёв и карточками, а сканер работает в источнике раньше профиля.

### Срезы реализации
1. Модель профиля и каталог правил; перенос констант детекторов в профиль; `ConventionPack` собирается из профиля. Поведение по умолчанию не меняется (тесты зелёные).
2. Хранилище и `GET/PUT /api/profile?path=` в Map, DTO в Contracts, передача профиля в Analysis.
3. Интерфейс: выбор уровня, таблица правил, подсказка уровня.
4. Новые правила методички как детекторы — по одному, отдельными задачами: смесь стратегий ошибок, избыточный `ThrowIfNull`, даты и события в агрегате, двойная валидация, папки не по сущности.

## Статус реализации
- **Срез 1** (модель профиля, каталог правил, применение, пороги и имена сервисов, словарь ролей) — в `dev`.
- **Срез 2** (хранилище и API): Map хранит конфигурации и привязки «проект → конфигурация» в JSON-файле данных пользователя (`Profiles:Directory`, по умолчанию `~/Library/Application Support/arch_forge/profiles.json`). API Map: `GET /api/rules`; `GET/POST /api/profile/configs`, `GET/PUT/DELETE /api/profile/configs/{id}`, `POST …/{id}/duplicate`; `GET/PUT /api/profile?path=`. Analysis: `POST /api/system` с профилем в теле и `GET /api/rules`. `GET /api/system` через Map сам берёт профиль привязанной конфигурации. Вход проверяется единым `ProfileValidator` (контракт) и в Map, и в Analysis. Аутентификации на этих эндпоинтах пока нет (локальное приложение; вход — ADR 0013).
- **Срез 3** (окно «Профиль проекта», `frontend/src/ProfileView.tsx`): открывается из панели «Вид». Выбор уровня, свои конфигурации (создание, копия, импорт и экспорт JSON, сохранение версией, удаление), строгость правил с источником значения и сбросом (правило, категория, к уровню, к родителю), пороги, словарь ролей, имена сервисов, применение к проекту. Встроенный уровень не меняется: первая правка создаёт несохранённую копию. Сохранение или удаление применённой конфигурации пересчитывает проект. Импорт пропускает только допустимую форму данных, окно обёрнуто в границу ошибок. Добавлен `GET /api/vocabulary` (встроенные значения как точка отсчёта отличий). **Не вошло и вынесено в отдельные задачи:** конструктор своих правил, предпросмотр влияния на проект, подсказка уровня по коду, примеры «плохо / хорошо» и число найденных типов у маркеров, импорт по коду из каталога (после системы публикаций).
- **Предпросмотр влияния (#127):** `POST /api/profile/preview?path=` (Map → Analysis `POST /api/system/preview`) считает находки по проверяемому профилю и по чистому уровню (по строгости и по правилам), совет уровня с причинами (число сервисов, брокер, доля маркерных интерфейсов; очки перечислены, уровень молча не меняется) и число типов у маркеров и суффиксов словаря. Каталог правил отдаёт примеры «плохо / хорошо». Чтобы правка не читала код заново, разбор Roslyn кешируется (`ScanCache`): ключ — нормализованный путь, отпечаток — хеш по пути, времени и размеру всех `.cs`, `.csproj` и `Directory.*.props`; срок 10 минут, деградированный результат (откат на синтаксический пол) — 30 секунд; «Пере-анализировать» сбрасывает кеш (`refresh=true`). Одновременно считается не больше двух предпросмотров. Лимиты словаря строже: до 32 маркеров и запасных признаков и до 16 суффиксов на роль (каждый суффикс — ожидание для каждого типа проекта).
- **Защита API профилей** (после security review): профиль ≤ 64 КБ в сериализованном виде, тело запроса ≤ 256 КБ, до 200 конфигураций и 1000 привязок (лимиты проверяются атомарно в хранилище); изменяющие запросы с `Sec-Fetch-Site: cross-site` отклоняются (`CrossSiteGuard`), `AllowedHosts` ограничен localhost/127.0.0.1/[::1] (защита от DNS rebinding); файл пишется атомарно с `fsync`, повреждённый или созданный более новой версией не затирается, в ответе клиенту нет пути к файлу. Известные ограничения: один процесс Map на файл профилей; файл читается целиком на каждый запрос (кеш — при необходимости); аутентификации нет до ADR 0013.
- Пустое тело `PUT /api/profile` — ошибка, сброс привязки — `{}`. Падение Analysis или файла даёт 503 с понятным текстом, а устаревший профиль не прячет карту: показывается разбор по умолчанию и пометка в `degradations`.
- Своё правило из шаблона (конструктор) в формат пока не входит: анализатор не умеет его проверять, это срезы 3–4. Формат манифеста версионирован (`FormatVersion`), добавим опциональным полем.

## Не входит
Автоматический импорт методички из Obsidian (в репозитории хранится снимок каталога правил со ссылками на заметки); смена движка Roslyn; другие языки.

## Альтернативы
- **Только JSON-файл.** Остаётся как есть: неудобно и недоступно, если нельзя править чужой репозиторий.
- **Один жёсткий свод для всех.** Давит маленькие проекты и порождает недоверие к находкам.
- **Автоопределение уровня без выбора.** Ошибётся на нетипичном проекте и нарушит принцип «не выдумываем».

## Последствия
- Находки становятся осмысленными для малого проекта и строгими для платформы.
- Появляется поддерживаемый реестр правил, на который опираются Фаза 2 (агент знает целевой уровень) и Фаза 3 (арх-линты в CI с профилем как gate).
- Цена: новая модель и хранилище настроек; снимок каталога правил надо синхронизировать с методичкой.
