# 0011 — Позиционирование: картина системы (env-aware) + кросс-сервисное ревью; две оси навигации

## Статус

Опирается на [0004](0004-full-vision-thin-mvp0.md), [0009](0009-dotnet-roslyn-microservices.md), [0010](0010-frontend-own-client.md). Согласовано на интерактивном прототипе (`docs/prototype-notes.md`); декомпозиция — `docs/roadmap-epics.md`.

## Контекст
Фаза 1 доказала путь «разбор → карта» и дала код-как-плашку (single- и мульти-сервис). Возник вопрос ценности против «просто открыть в Visual Studio»: на **одном** сервисе IDE не хуже. Проверка показала, что ценность arch_forge — на **системном** уровне: много сервисов, чужой код, конформанс к своду, DevOps-картина. Через серию мокапов и кликабельный прототип согласована модель интерфейса и навигации. Её нужно зафиксировать, чтобы декомпозиция и реализация шли не «из головы».

## Решение

**Главный сценарий.** Увидеть **всю микросервисную систему по окружениям** (dev/stage/prod) и **найти кросс-сервисные проблемы** (арх-ревью). Код-как-плашка (Фаза 1) — **подложка**, не самоцель.

**Две ортогональные оси навигации.**
- **Масштаб** (хлебные крошки): `System (L0) → Service (L1) → Layer (L2) → Type → Member`. Погружение — двойной клик; крошки ведут вверх.
- **Вид/линза** — что смотрим на текущем уровне.

**Виды системного уровня (L0):**
- **Структура** — топология: сервисы + хранилища/шина + **связи** (`http-call · rw-db · uses-bus`). Клик по ребру → что по нему идёт (запросы/операции/события).
- **Deploy** — та же топология + порты/сети/healthcheck/порядок старта, состояние **по выбранной среде**.
- **Сравнение сред** — дифф dev/stage/prod (что меняется и ломается к prod).
- **Поток** — кросс-сервисный трейс сценария.

**Виды уровня сервиса (L1):** Слои/типы · Endpoints · **DI** (контейнер сервиса).

**Спорные решения (зафиксированы):**
- **Поток = системный уровень**, но навигация **деревом «сервис → endpoint»**: трейс кросс-сервисный, точка входа — endpoint конкретного сервиса.
- **DI = уровень сервиса** (у каждого свой контейнер), открывается при выборе сервиса, а не как системная вкладка.

**Доверие / провенанс — сквозной инвариант UI.** У каждого ребра, находки и конвертации данных: **источник** (`файл:строка`), **уверенность** (маркер vs эвристика), **«почему»** (доказательство) и **переход в код**. Это прямое продолжение «якоря на исходник» из `VISION.md`.

**Единый инспектор.** Любой выбор (узел / связь / находка / слой / тип / шаг потока / DI / сравнение) рендерится по одной структуре: метка «что выбрано» + заголовок + подзаголовок + секции. Функции связаны (узел → его связь → что по ней идёт → откуда в коде).

**Повторяющиеся блоки.** Однотипные узлы, которые есть у каждого сервиса (`*-migrations`, `postgres-*`, `*-export`, `$*` конфиги, инфра), авто-детектятся по имени и **скрываются фильтром** (не удаляются); привязаны к сервису-владельцу и живут в его области `src/Services/<svc>`.

## Альтернативы
- **Фокус на single-service (как IDE).** Отклонено: на одном сервисе IDE не уступает; преимущество — на системном уровне (кол-во сервисов × незнакомость × важность конформанса).
- **Только код-дрилл, без DevOps/сред.** Отклонено: недостаточно, чтобы «увидеть систему полноценно» — не видно портов/сетей/зависимостей и различий сред.
- **Плоские вкладки без осей уровней** (Структура/Deploy/Поток/DI рядом). Отклонено: путало — Поток и DI разного масштаба. Разведено по осям уровень×вид.

## Последствия
- **Дополняем, не заменяем.** Модель наращивает существующее приложение (Фаза 1), а не переписывает его: готовый функционал (drill, инспектор, панель проблем, ортогональные рёбра, импорты, покрытие и т.д.) сохраняется. Переорганизация UI (блоки левой панели, единый инспектор) сохраняет всё существующее поведение и контролы — меняется только форма. Удаление функционала — только с явным обоснованием и согласованием.
- Вводится **Фаза 1.6** — env-aware картина системы + DevOps-слой (инкремент поверх Фазы 1); drill `L0→L1→L2` остаётся ядром навигации. **Фаза 2 (ИИ) и Фаза 3 (контроль) — как в `VISION.md`, не меняются** (диффы/CI/шаринг = Фаза 3).
- Требуется парсинг **compose + env-оверрайдов + сетей** (расширение `ComposeSystemSource`) и статический **call-graph** для потоков; провенанс — обязательный атрибут каждого факта.
- Эпики и задачи — в `docs/roadmap-epics.md`; согласованный эталон интерфейса — прототип (`docs/prototype-notes.md`).
- `VISION.md` дополнен акцентом на картину системы; DoD Фазы 1 остаётся в силе как подложка.
